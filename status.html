Read this first

Player surnames are out of the public data Structural, not cosmetic

A shared team's documents are readable by anyone — no sign-in, no follow. Shortening names in the web page only changed what was drawn; the surname was still one fetch away. And "approved follower" was never a gate on a public team, because following one is approved automatically.

Surnames now live in teams/{id}/rosterPrivate behind canSeePlayerNames — staff, or an approved follower of a non-public team. Everything public carries "Hayden H." Three Cloud Function triggers hold that on every write, so it holds for every app version. 247 existing surnames migrated; the verifier reports zero world-readable documents still carrying one.

Family links work end to end Web + app

A follower picks a player, says how they're related, and staff approve. Coaches can decide them too — they were already being emailed about every request while unable to act on one. One Followers section on the team page shows each person, the player, and the relationship, with approve, change and remove. The same list is in the app's sharing section. Followers can change their own relationship (which goes back for approval) or stop following.

Videos are tied to the players in them

Reels are built per player, but nothing recorded which player — the builder knew as it wrote each file and handed back only a filename. Now recorded at build, published at upload, and listed on the player's page behind canSeePlayerVideos. Deliberately not on the game document: an unlisted YouTube link works for anyone holding it, so a list of every video of one child is the sensitive thing itself, not a pointer to one.

Fixed the last two days

Editing a player didn't reach anything

Add a player as "Audrey", add the surname later, and the roster kept showing "Audrey" — the roster stored its own copy at add time and nothing refreshed it. The player now owns their name; number and position stay per-team, because the same kid really does wear 7 here and 12 there. Then the same staleness turned up in the cloud, so the web page still showed the old name: renaming now pushes to every team they're on, and your existing teams have been repaired.

Removing a player from a roster

The ✕ deleted immediately and permanently, on a screen with a Save button. It now asks, says what it costs, and waits for Save — marked rows stay visible, struck through, with undo. Removing the last player also never reached the cloud at all: the sweep that infers removals is guarded against stale caches, so deliberate removal now names the player instead of being inferred.

"Anonymous" followers

The email invite looked the person up by address and then never saved their name. Fixed at the invite, fixed when reading, and your existing followers repaired.

Web: unreadable box, signed-out top bar, mobile layout on desktop

The Find Teams description used a variable that doesn't exist, so it fell through to the browser's visited-link purple — and even corrected, that grey measured 2.5:1 against the panel, so it changed colour as well. The account bar showed "Sign In" after a Back because the repaint only ran once the team document had loaded; it now repaints on every auth event and on a bfcache restore. And above 900px the pages are a centred 760px column instead of stretching edge to edge.

What the numbers actually say

"10 new users" was 2

7 were automated signups matching name.NNNNN@gmail.com — they authenticate against Firebase Auth directly, never open the app, and write nothing. 3 were anonymous web sessions from the scoring page, which were never signups. The digest read a collection nothing had written in months; it now reads Auth itself and labels every account. Over 30 days: 39 accounts, 4 recorded a game.

59% of push tokens are dead — and that's churn, not a bug

41 of 99 are deliverable. Dead rate tracks time since last app open (33% within 7 days → 68% past 90), which is the shape of uninstalls. The token refresh path was already correct. A failed send now stamps uninstalledAt so it reads as a retention metric. This is why the email matters: it reaches people the app can't.

To do — not started

Create a player without creating a team You asked · not started

There's no way to add a player on their own, and no single screen holding everything about them. That's where the extra player detail belongs, and where you'd build a player up before a team exists.

Edit-feature clips aren't tied to a player

Stat-driven reels index against the player they're of; clips made with the edit feature upload with no player attached, so they don't appear in a player's video list.

Cross-team match requests have no in-app screen

A guardian is asked on the web dashboard and by email. The plumbing is done and tested; there's no equivalent surface in the app yet.

Cross-device roster resurrection

A second device still holding a removed player re-uploads them on its next sync — roster membership has no tombstone, unlike deleted players. Same shape as the "Greg" bug.
